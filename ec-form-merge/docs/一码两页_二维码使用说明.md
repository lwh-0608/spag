## 两种码，分工不同

| 码 | 链接 | 什么时候用 | 扫码到能填 |
|---|---|---|---|
| **公网码**（默认） | `https://datafusion.a.pinggy.link/checkin` | 客人用 4G/5G 流量、或会场外的场景 | 受国际链路影响，**数秒到十几秒**，高峰期更慢 |
| **局域网码**（现场推荐） | `http://<这台 Mac 的局域网 IP>:8888/checkin` | **客人手机连了会场 WiFi**（和这台 Mac 同一网段） | **几十毫秒，秒开** |

现场判断很简单：**连了 JFC 会场 WiFi → 扫局域网码；没连 WiFi → 扫公网码。**
两种码并存，互不冲突；公网隧道断的时候，局域网码照样能用（只要 Mac 和 WiFi 正常）。

> 局域网地址会随 WiFi/重连变化，**每次活动开始前重跑一遍**生成：
> ```bash
> cd ~/Desktop/待办事件
> /Library/Frameworks/Python.framework/Versions/3.13/bin/python3 KPI冲刺/英语角/make_ec_lan_qr.py
> # 产物：KPI冲刺/英语角/二维码/LAN/（3 张码 + 合并页 A5 桌卡）
> ```

## 页面加载优化（2026-11-24 晚）

用户反馈「扫码进入时间很长」。实测拆开看：

- 本机 Flask 渲染/响应：**4–25 ms**（不是服务端慢）
- 公网 Pinggy 链路（健康时）：TLS 1.0–1.5s + TTFB 3.1–4.6s + 传输 ≈ **3.4–5.6s**，且晚高峰会退化为超时/断连
- 会场局域网：**8 ms**

因此做了两件事：

1. **页面瘦身**：内联 logo 由 7.7KB WebP（base64 10.3KB）重压为 300px 宽 WebP（base64 5.0KB）；
   整页 gzip 由 **22.2KB → 17.9KB（-19.6%）**，公网传输少约 4.3KB。
2. **补上局域网合并码**：现场 WiFi 下扫码秒开（原有 LAN 码只覆盖报名/签到/反馈旧入口，合并页这次补齐 A5 桌卡）。

> 公网链路的 TTFB 是 Pinggy 边缘与跨境链路决定，本地无法再优化；
> 若要求公网也快，需要考虑换隧道服务（另有评估）。

## 决策记录
